# 故障排查、备份与赛场应急

正常协作默认允许联网并使用 GitHub；本项目不把离线缓存、PWA 或自动断网恢复作为承诺能力。网络、供电或服务异常时，先保护人员、设备和已有文件，再恢复协作。

## 快速分流

| 现象 | 先做什么 | 不要做什么 |
| --- | --- | --- |
| CLI 不能运行 | 确认 Node.js 版本、依赖安装和构建结果 | 不随意删除仓库或重装系统 |
| JSON 校验失败 | 阅读 `npm run validate` 输出的文件和字段错误 | 不跳过校验直接提交 |
| `networkError` | 保留本机工作，记录时间和状态，等待网络恢复 | 反复推送、切换远端或借用他人账号 |
| `authError` | 本人通过 GitHub/系统凭据管理器重新认证 | 把令牌贴到聊天、JSON 或仓库 |
| `conflict` / `diverged` | 执行冲突停手清单 | force、rebase、reset、merge、stash |
| 突然断电 | 先确认人身与设备安全，恢复供电后检查文件与 Git 状态 | 未检查就继续提交或接电机 |

## 赛场断网应急

1. 立刻停止拉取和推送；不要因网络失败重新初始化仓库。
2. 在本机继续实验时记录时间、操作者、设备状态、文件和测试结果。若 CLI 不可用，可先写纸质记录或本机临时文本，恢复后转成事件/问题。
3. 不要让三人同时编辑同一个任务、问题或已认领想法 JSON。断网时尤其坚持单写者。
4. 若必须在本机提交，先确认提交只含本人已核对的文件；提交说明写清“本机待同步”。网络恢复后，先“检查远端”，再按五步流程处理。
5. 恢复网络后若显示 `behind`、`diverged` 或 `conflict`，立即转到冲突手册；不能假设自己的本机版本最新。

## 赛场断电应急

1. 先断开电池、大电流电源和电机驱动，确认没有发热、异味、短路风险。
2. 记录断电时：电源域、设备连接、程序/提交版本、正在执行的任务或问题 ID。
3. 恢复供电按“限流 → 电源域 → 核心板/下载 → 空载执行器 → 外设”的顺序，不直接全系统带载上电。
4. 电脑恢复后先看 Git 状态和文件修改时间；JSON 无法解析、编辑器恢复临时文件或出现未知改动时，创建问题并保留原件，不自动覆盖。
5. 对设备重新完成最小自检并写 `testResult` 事件；没有复测证据，不关闭问题。

## 备份策略

### 正常状态

- 已推送到团队 GitHub 的提交是跨电脑同步副本；每天收尾确认关键提交已推送。
- 重要实验照片、串口日志和测量数据要关联到任务/问题/事件，注明采集电脑与时间。
- `.本机配置/`、`.看板缓存/`、账号凭据和系统密钥不进入 Git，也不作为团队备份内容。

### 应急静态副本

GitHub 或网络不可用但需要保全材料时，由队长指定一人把**当前工作区的非敏感资料**复制到可信移动存储，并在纸面或事件中记录：时间、来源电脑、当前短提交号、是否有未提交改动、复制人。不要复制 `.git/`、`node_modules/`、本机配置、令牌、浏览器配置或不明大文件。

该副本是灾备证据，不是新的协作真源。网络恢复后必须回到原仓库，检查远端并按正常流程同步；不要让移动盘副本和仓库同时被多人编辑。
