# 每日赛前、比赛中与交接流程

## 每日赛前：10 分钟站会

三人在各自电脑打开终端，按顺序完成：

1. 执行 `npm run git:status`，确认没有 `conflict`、`diverged`、认证或网络错误。
2. 执行 `npm run git:pull`；拉取后再检查一次。
3. 执行 `npm run overview`：每人说清今天的一个主任务、一个验收条件、一个最可能的阻塞。
4. 核对 `critical`、`high`、`blocking: true` 的问题，先定 owner 和下一次复查时间。
5. 核对想法，只把当天需要验证的想法提升为任务；没有证据的不强行定案。
6. 队长创建或更新一条事件，记录当天目标、人员在场情况和重大风险。

任何成员未同步到相同提交、身份未登记或 Git 状态异常时，先处理协作基础，不把关键任务分派给该成员。

## 比赛中：创建事项的最小流程

### 创建任务

适用于“有明确产出和验收”的工作。

1. 先搜索是否已有同类任务，避免重复。
2. 填标题（动词 + 对象）、模块、优先级、说明、验收条件。
3. 指定一个 `owner`；多人协作只写入 `participants`，不设双 owner。
4. 开始时改为 `doing`；受问题影响时关联 `blockingIssueIds` 并改为 `blocked`。
5. 复测通过、验收条件逐项完成后进入 `review` 或 `done`；补测试事件和相关提交号。

### 创建问题

适用于“出现异常、不能复现、影响进度或需要决策”的情况。

1. 标题写现象，而非猜测原因，例如“上电后电机通道 B 无输出”。
2. 写可复现的 `symptoms`：条件、现象、频率、已排除项。
3. 标 `severity` 和 `blocking`，关联受影响任务，指定一个 owner。
4. 有临时绕过方式时写 `workaround`，不要把绕过当作解决。
5. 修复后写 `resolution`、复测证据事件和关联提交；确认后才设为 `resolved`。

### 创建想法

适用于“可能可行但还没有证据”的建议。

1. 写目标、假设、需要验证的条件与风险。
2. 保持 `open`，不因讨论热烈就升级为结论。
3. 队长或 owner 决定验证时，提升为有验收条件的任务；不采用时标记 `discarded` 并用决策事件说明原因。

## 交接：离开前 3 分钟

离开的人不能只说“差不多了”。对每个进行中或阻塞事项：

1. 确认主记录的 owner 正确；不是自己继续负责就使用交接流程转给接手人。
2. 新建 `handoff` 事件，至少写：已完成、未完成、当前现象、下一步第一动作、文件/设备位置、风险、关联提交号。
3. 接手人先阅读事件并口头确认，再开始改主记录。
4. 交接后重新检查 Git 状态。未推送的提交要明确告诉接手人“仅在某电脑”，并优先在网络正常时按五步流程推送。

可直接填写：

```text
【交接】事项：<任务/问题 ID>
已完成：<证据或结果>
未完成：<剩余步骤>
下一步：<接手人第一步>
位置/版本：<设备位置、分支、短提交号或文件>
风险：<可能出错点>
```

## 每日收尾

1. 所有成员各自查看未提交文件；不认识的改动不要提交。
2. 已完成且应共享的内容按“提交 → 推送”五步同步。
3. 队长检查是否仍有只在一台电脑上的关键提交、未分配 blocker、没有 owner 的进行中任务。
4. 记录当天最后一条全局事件：已完成、遗留问题、明日第一优先级。
5. 断开设备电源前按设备核对表记录最后状态；不要把“关机前能跑”当作没有证据。
