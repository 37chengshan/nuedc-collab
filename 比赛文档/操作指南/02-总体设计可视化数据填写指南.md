# 总体设计可视化数据填写指南

权威持久化画布为 `比赛设计/总体方案/系统画布.json`。当前协议的实际 Schema 只接受本页列出的字段；不要把网页内部展示需要的 `responsibility`、`inputs`、`outputs`、`x`、`y` 等字段直接塞进该 JSON，除非后续 Schema 已明确更新。

可从 [`../设计模板/总体设计画布模板.json`](../设计模板/总体设计画布模板.json) 复制开始。模板描述“赛题分析”阶段，不表示最终方案。

## 顶层字段

| 字段 | 类型/允许值 | 填写规则 |
| --- | --- | --- |
| `schemaVersion` | 固定数字 `1` | 不改。 |
| `title` | 1–200 字符 | 写当前画布名称，如“赛题分析画布”；不要写未经确认的最终结论。 |
| `phase` | `赛前准备` / `赛题分析` / `方案设计` / `实现验证` | 选当前所处阶段。 |
| `nodes` | 数组 | 一个模块/能力一个节点。 |
| `edges` | 数组 | 一条已确认或待验证的关系一条边。 |
| `context` | 对象 | 链接已有问题、事件和资料 ID。 |
| `updatedAt` | 带时区 ISO 8601 | 如 `2026-07-29T09:30:00+08:00`。 |

## 节点与连线

每个节点必须有：

| 字段 | 写法 |
| --- | --- |
| `id` | 画布内唯一、稳定的 ASCII 标识，如 `vision`、`control`，不要随意改名。 |
| `label` | 给队员看的中文名称，例如“视觉实验能力”。 |
| `status` | 当前事实状态，如“待验证”“已测通”“赛前准备”；不要用它暗示最终选题。 |
| `module` | 可选。与任务看板使用的模块名保持一致，例如“MSPM0”“K230 视觉”。 |

每条边必须有：

| 字段 | 写法 |
| --- | --- |
| `from` | 已存在的起点节点 `id`。 |
| `to` | 已存在的终点节点 `id`。 |
| `label` | 关系说明，如“状态输入”“供电”。没有证据时写“待验证接口”，不要虚构协议细节。 |

## context 关联

`context` 三个数组必须都存在，没有内容写空数组：

```json
{
  "linkedIssueIds": [],
  "linkedEventIds": [],
  "linkedMaterialIds": []
}
```

- `linkedIssueIds`：关联现有 `I-...` 问题，例如接口不稳定或电源异常。
- `linkedEventIds`：关联已有 `E-...` 测试、决定或交接证据。
- `linkedMaterialIds`：关联资料条目的稳定 ID；不能确认 ID 时先留空，不把文件路径冒充 ID。

## 填写顺序

1. 赛题公布后先保存官方原文，在需求录入模板中分离“原文事实”和“待确认项”。
2. 新建或复制画布模板，将 `phase` 改为 `赛题分析`。
3. 只画已经存在的能力边界和题目明确要求；未决定的方案用节点状态和想法/问题记录，不用图形假装已决定。
4. 每次技术决定或实测后追加事件，再把对应事件 ID 加入 `context`。
5. 提交前检查：节点 ID 唯一、每条边两端都存在、时间有 `+08:00`、没有添加 Schema 未定义字段。

画布是概览，不替代方案比较、接口约定、测试记录和问题单。
